# 短链服务设计说明

## 1. 项目边界

当前项目是 Java 21、Spring Boot 3.3.5 的单机内存短链服务。数据保存在 `ConcurrentHashMap` 中，重点验证短链幂等、盲盒解析、并发扣减、HTTP 跳转和断链检测等核心业务规则。

当前实现不引入数据库、缓存、消息队列或分布式协调组件。

## 2. 短码设计

### 2.1 为什么使用 Base62

Base62 使用数字、小写字母和大写字母，适合放在 URL path 中，不需要额外转义。相比纯数字，同样长度可以表达更大的编码空间；相比 Base64，不包含容易产生 URL 转义问题的字符。

### 2.2 关于短码长度

已经确认的实施基线将默认短码长度设为 7 位，并支持配置为 6、7、8 位。当前运行配置也使用 7 位。

配置长度只影响后续新生成的短码；校验器始终接受 6、7、8 位。这样从 7 位切换到 6 位或 8 位时，历史短码不会仅因为长度变化而失效。当前项目使用内存存储，应用重启后数据本身不会保留，这是存储层限制，不是短码长度校验导致的失效。

7 位 Base62 的理论空间是 `62^7`，约为 3.5 万亿，能够显著降低高规模场景下的碰撞概率。因此 7 位作为默认基线更适合生产规模；6 位仍可用于演示或兼容场景，8 位则适合更大规模的编码空间需求。

### 2.3 全局唯一性

短码生成器使用 `SecureRandom` 生成 Base62 字符串。生成后由 Repository 使用 `ConcurrentHashMap.putIfAbsent` 原子保留短码；如果发生碰撞，Service 最多重试 10 次，超过上限抛出 `ShortCodeGenerationException`。

`containsKey` 后再 `put` 不是安全方案，因为两个线程可能同时检查到不存在，然后互相覆盖。`putIfAbsent` 将检查和写入合并为一个原子操作。

## 3. 普通短链幂等

普通短链使用：

```text
normalizedUrl + "|" + normalizedChannel
```

作为业务唯一键。这样相同 URL、相同渠道会返回同一个短码；相同 URL、不同渠道会生成不同短码。业务键通过 `ConcurrentHashMap.computeIfAbsent` 原子计算，避免并发重复创建。

URL 会校验协议、host 和长度，并规范化 scheme、host；渠道会去除首尾空格，未传或空白渠道统一为 `default`。

## 4. 访问计数和盲盒次数

### 4.1 普通短链访问计数

普通短链的 `resolveCount` 使用 `AtomicLong`，因为访问次数可能长期增长，并且多个请求会并发更新。解析时使用 `incrementAndGet()`，不会使用非原子的 `resolveCount++`。

### 4.2 盲盒有效次数

盲盒的剩余次数使用 `AtomicInteger`。消费逻辑通过 CAS 循环实现：

1. 读取当前值；
2. 当前值小于等于 0 时失败；
3. 使用 `compareAndSet(current, current - 1)` 尝试扣减；
4. CAS 失败则重新读取并重试。

不能使用 `get()` 后直接 `decrementAndGet()`，因为检查和扣减之间存在竞态窗口，多个线程可能同时通过检查并造成超发。

只有 CAS 成功后才允许随机选择 URL 和增加访问次数。CAS 成功将剩余次数变为 0 后，状态更新为 `EXHAUSTED`。状态用于展示和快速失败，但盲盒是否允许解析最终以 CAS 结果为准。

领域对象禁止在剩余次数大于 0 时直接设置 `EXHAUSTED`，从而保持状态和次数一致。

## 5. 随机选择

`DefaultBlindBoxSelector` 使用 `ThreadLocalRandom.current().nextInt(candidates.size())` 选择下标。每个下标拥有相同的选择范围，因此候选 URL 的理论概率相同。

Selector 只负责选择，不负责扣减次数，也不修改候选列表。随机测试只验证合理比例区间，不要求完全平均。

## 6. 内存存储和查询

Repository 使用 `ConcurrentHashMap` 保存短链，并返回集合副本；领域对象中的原始 URL 列表使用不可变副本保存，响应 DTO 不直接暴露领域对象或原子类型。

条件查询当前执行内存全量扫描、过滤、排序和分页，复杂度约为 O(n)。这适合笔试和小规模数据，不适合大规模生产数据。

## 7. HTTP 跳转和状态

`GET /s/{shortCode}` 和解析详情接口都会执行真实解析。普通短链返回唯一 URL；盲盒先消耗次数，再随机返回 URL；成功解析后访问次数原子增加。

状态规则集中在 `LinkStatusPolicy`：

- `ACTIVE`：允许解析；
- `BROKEN`：抛出断链异常；
- `EXHAUSTED`：抛出盲盒次数耗尽异常。

异常统一转换为 JSON 响应，断链和次数耗尽使用 HTTP 410 Gone。

## 8. 断链检测

健康检测使用 Spring 管理的单例 Java `HttpClient`。单次请求默认超时 3 秒，连接超时 2 秒；先发 HEAD，收到 405 后降级 GET，GET 使用流式响应并立即关闭，不读取完整响应体。2xx 和 3xx 视为可达，客户端不自动跟随重定向。

健康检测只负责检测 URL，是否自动标记 `BROKEN` 由 Service 决定。普通短链检测一个 URL，盲盒检测全部候选 URL；盲盒只要有一个 URL 可达，整体就视为可达。

## 9. SSRF 防护

主动请求用户提供的 URL 存在 SSRF 风险。请求前首先限制协议为 HTTP/HTTPS，并解析 host。除了检查 `localhost` 字符串，还通过 `InetAddress` 检查解析结果，拒绝回环、私有、链路本地、site-local、组播、未指定地址以及 IPv4-mapped 私有地址。

DNS 解析失败返回不可达结果，不向客户端返回服务器内部网络信息。HttpClient 默认不自动跟随重定向，因此 3xx 只表示原目标服务可达，不会自动访问未经重新校验的重定向目标。

## 10. 批量检测线程池

批量检测使用独立的有界 `ThreadPoolTaskExecutor`：

- 核心线程数：4；
- 最大线程数：8；
- 队列容量：100；
- 空闲线程保活：60 秒；
- 拒绝策略：`CallerRunsPolicy`；
- 关闭时等待任务完成并释放线程池。

`CompletableFuture` 显式传入该 Executor，不使用 `ForkJoinPool.commonPool`，也不使用 `parallelStream`。每个任务独立转换异常为结果，单条失败不会导致整批失败。

## 11. 多实例一致性问题

当前数据只在单个 JVM 内存中。多实例部署后，不同实例可能看不到彼此创建的短链，盲盒次数也会在不同实例分别扣减，导致短码唯一性和有效次数一致性失效。

## 12. 生产环境演进

生产环境可以按以下方向演进，但不属于当前项目实现范围：

1. 使用 MySQL 持久化短链元数据；
2. 使用 Redis 缓存热点短链；
3. 使用 Snowflake 或号段模式生成全局 ID；
4. 使用 ID 转 Base62 生成短码；
5. 使用 MQ 异步记录访问日志；
6. 使用 ClickHouse 或 Elasticsearch 做访问分析；
7. 使用定时任务执行断链检测；
8. 使用分布式锁或数据库乐观锁控制盲盒次数；
9. 部署多实例并将状态迁移到共享存储；
10. 增加限流、监控、告警和审计。

生产化时还需要重新评估 DNS rebinding、重定向目标校验、网络出口策略和健康检测并发上限。
